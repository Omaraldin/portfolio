## The problem this site has to solve

Omar has shipped across an unusually wide range of fields. Employers read that
breadth as a risk: *will this person be satisfied in the role we're hiring for?*

The site has to reframe breadth as depth. The argument: the transferable skill is
system design and data flow — being able to architect a correct, performant
system in a technology he has not used before. Not a "weak generalist" who knows
a little of everything.

Two features carry that argument:
- **Dynamic CV per job profile** — send a backend recruiter the backend CV.
- **Capabilities as a first-class axis**, separate from domains. Organise by what
  he can do, not by what he has touched.

Second purpose: publishing his own writing about the tech industry. Not just a
project showcase.

## The admin panel

Runs at `/admin` during `bun run dev` only. Writes straight to the files above;
the dev server picks changes up immediately. To publish, commit the changed
files and deploy.

It has no authentication, which is safe only because it cannot be deployed:
admin route files use a `.dev.tsx` extension that `next.config.ts` only accepts
while developing, so a production build contains no admin routes at all. The
route handlers also throw in production as a second, independent guard. Do not
rename those files to plain `.tsx`.

`tsconfig.json` excludes `.next/dev` for the same reason. That directory holds
route types generated by `next dev` which describe the admin routes; a
production build excludes those routes, so type checking the manifest would
fail whenever a dev server had run.

The article body has a split-view editor: MDX source on the left, live preview
on the right, scrolling together. The preview compiles through the same rehype
plugins the published page uses — including shiki, so code blocks are
highlighted exactly as they will ship, in both themes. It renders markdown
rather than MDX, so a JSX component in the body previews as literal text; the
published page remains the source of truth.

On project count: there is no target. The matrix derives its axes from whatever
the projects cover, so the only rule is that a claimed domain must have work
behind it. Home shows the 4–5 with the widest spread; `/work` shows everything.

## Certifications (placeholder)

The two entries in `src/data/certifications.json` are invented and must be
replaced. Only the name and issuer are required; issue date, expiry, credential
ID, verification link, and the certificate document are each optional and are
simply not rendered when absent.

`/certifications` is the main surface: a grid of document thumbnails, each
opening the full certificate in an overlay. Entries also appear as a compact
strip on the home page (those marked `featured`), as a list on `/about`, and as
a condensed block on every CV profile. An entry whose expiry has passed is
labelled "lapsed" rather than hidden, so currency stays visible.

Documents are paths under `/public`, e.g. `/certificates/aws.pdf`. A PDF has its
first page rendered to a thumbnail by pdf.js; an image is used directly. Both
are shown `contain` rather than `cover`, because cropping a certificate loses
the border and seal that make it recognisable.

pdf.js loads its worker over HTTP, so `public/vendor/pdf.worker.min.mjs` is
copied from the installed package by the `sync-pdf-worker` script on every dev
and build. It is gitignored — do not check it in, and do not remove the script,
or PDF thumbnails silently stop rendering.
